## KEY FINDING — reason is `insufficient_funds`, NOT `webhook_declined`
`stripe_money.authorize()` (stripe_money.py:182) creates the authorization via
`POST /v1/test_helpers/issuing/authorizations`, which CAPTURES against the test Issuing
balance. The test balance is $0 (US test accounts can't be funded), so Stripe declines
EVERY authorization with `insufficient_funds` at the funding check — BEFORE real-time
decisioning runs. So:
  * Even the brain-APPROVED scenes (s2 40c, s3 30c) were declined by Stripe (funding),
    not by the spending_controls limit and not by our webhook.
  * No `issuing_authorization.request` event is ever emitted (only `.created`), so
    `stripe listen --events issuing_authorization.request` forwarded NOTHING and the
    webhook never ran. `runs/webhook_decisions.jsonl` was never created.
  * `stripe trigger issuing_authorization.request` ALSO only produced an
    `issuing_authorization.created` event — confirming this account is NOT in
    real-time/synchronous decisioning mode.

## To get `webhook_declined` (Dennis-gated, account-level)
Real-time decisioning must be ENABLED in the Stripe dashboard (Issuing → settings →
register a webhook endpoint for `issuing_authorization.request`, putting the account in
synchronous-authorization mode). Only then does Stripe emit `.request` and defer the
verdict to our webhook (which reads runs/active_budget.json and replies decline) — and
funding stops mattering because the decline happens at the request stage. This matches
the hedge already written in `.handoff-webhook-bridge.md` lines 124-132. The current code
path cannot reach `webhook_declined` on its own.
